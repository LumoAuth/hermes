# LumoAuth Guard for Hermes Agent v0.1.2 (`v0.1.2`)

**Release Date:** November 23, 2026  
**Tag:** `v0.1.2` (signed), commit `d52e41e96f71cb9ff70053a1e887bb3a2f20e7f0`

## Package

| Package | Registry | Version |
| :--- | :--- | :--- |
| `lumoauth-hermes` | PyPI | `0.1.2` |
| `lumoauth/hermes` | GitHub, for `hermes plugins install` | tag `v0.1.2` |

The Hermes plugin name is `lumoauth`. Like 0.1.1, this release follows version 1 of the [LumoAuth Guard contract](https://github.com/lumoauth/agent-guard).

This release makes the changes that the Hermes maintainers asked for when they reviewed the plugin for Hermes's plugin catalog. `doctor` no longer reads Hermes's `.env` file or looks for secret values in `config.yaml`. To find out whether Hermes would approve a call without asking, the Guard now asks Hermes's settings first. The Guard classifies and decides tool calls as before.

## Install

```sh
hermes plugins install lumoauth/hermes --enable --yes-deps
hermes lumoauth setup
```

Hermes scans every plugin before it installs it. The scan reports that this plugin names credential paths such as `~/.ssh`, and asks you to confirm. The Guard names those paths to protect them, so answer `y`. In a script, add `--force` to the install command.

Setup asks for your LumoAuth dashboard address, a preset and where a person should approve calls. Then it prints a link, a code and a key fingerprint. Open the link, check that the code and the fingerprint match your terminal, and approve the agent. Then restart Hermes, or the Hermes gateway.

**Other ways to install:**

- **With pip**, in the Python environment that runs Hermes: `pip install lumoauth-hermes==0.1.2`, then `lumoauth-hermes setup`. Setup turns the plugin on in Hermes's `config.yaml`.
- **Pinned to this release:** `hermes plugins install lumoauth/hermes` follows the `main` branch. To stay on 0.1.2, pass the tag's commit: `hermes plugins install lumoauth/hermes --ref d52e41e96f71cb9ff70053a1e887bb3a2f20e7f0 --enable --yes-deps`. Hermes then refuses `update` for the plugin.

**Upgrade from 0.1.1 or 0.1.0:** after a git install, run `hermes plugins update lumoauth`. After a pip install, run `pip install -U lumoauth-hermes==0.1.2`. Your key and settings in `~/.lumoauth/guard/hermes/` stay as they are, so you don't need to run setup again.

**Requirements:**

- Hermes Agent 0.21.6 or later, on Python 3.11 or later.
- A LumoAuth organization. The Guard works on every LumoAuth plan. Approvals in the LumoAuth app, Slack and Discord need the Agent Governance add-on.

The package depends only on `cryptography` and `httpx`, which Hermes Agent already installs.

## What Changed

### 1. `doctor` No Longer Reads Hermes's Secrets

Hermes doesn't let plugins read its `.env` file or the secret values in `config.yaml`, even when nothing leaves the machine. In 0.1.1, `doctor` did both. Now:

- **Gateway checks use the environment.** The checks for gateway platforms and allow-lists (`hermes.allowed-users`, `hermes.approvers`) read the process environment. The `hermes` command loads `.env` into it when it starts, so `hermes lumoauth doctor` sees the same settings as before.
- **`secrets.plaintext` checks who may read `.env`.** It no longer counts API keys in `.env` or in `config.yaml`. It reports one of these:

  | Hermes's `.env` | Level |
  | :--- | :--- |
  | Missing, or readable by you only | `ok` |
  | Readable by its group | `warn` |
  | Readable by other users | `critical` |

- **`lumoauth-hermes doctor` says what it can't see.** Outside the `hermes` command, the environment doesn't hold Hermes's `.env`. `hermes.allowed-users` then reports `info`, says that it can't see the gateway settings, and suggests `hermes lumoauth doctor`. It still reports a `critical` finding that it can see.

A new test runs `doctor` with a `.env` file in Hermes's home, and fails if any file named `.env` is opened.

### 2. Hermes's Settings Come First in the Auto-Approval Check

When Hermes would approve a call without asking a person, the Guard blocks the call instead. Hermes approves without asking under `approvals.mode: off`, `--yolo`, `/yolo` and `hermes -z`. It also does so in an unattended context, such as cron, whose approval mode is `approve`.

Hermes has no public function that answers this whole question. The Guard now asks three sources in this order, and blocks as soon as one of them says yes:

1. `HERMES_YOLO_MODE` and `approvals.mode` in Hermes's config. The Guard always asks these, because they don't depend on Hermes's internal functions.
2. `tools.approval.is_approval_bypass_active()`, Hermes's own public check. It also sees `/yolo` turned on in a session.
3. Hermes's private approval helpers (`_yolo_active`, `_presence`, `_unattended_contexts`). Only they know about `hermes -z` and unattended contexts. They can only add a reason to block. When they are missing or change, the Guard does without them.

The Guard no longer calls `approval_context._get_approval_mode`.

### 3. Contract Note

The `secrets.plaintext` row of the contract's doctor checks (SPEC §9) now says what the check covers on Hermes. The contract stays at version 1, and nothing else in it changed.

## Known Limitations

The [limitations of 0.1.1](./v0.1.1.md#known-limitations) still apply. They include that the plugin isn't in Hermes's plugin catalog yet. This release answers the catalog review, and the catalog PR isn't merged yet. Two more details:

- **`doctor` no longer warns about API keys in `config.yaml`.** It can't look for them without reading the secret values. Hermes keeps API keys in `.env` when you set them with `hermes config set`.
- **`hermes plugins validate` still warns about the private imports.** The plugin still imports `tools.approval` for the helpers in step 3 above. The security scan still reports `caution`, because the plugin names credential paths such as `~/.ssh` in order to block them.
